# 출판일 저장 형식 정리

`books.pub_date`만 정리합니다. 날짜의 정확도를 보존하기 위해 컬럼은 `text`로 유지합니다.
회원 생년월일, 대출일, 등록일, 책의 등록번호와 ISBN은 변경하지 않습니다.

## 저장 기준

- 전체 날짜: `2000-08-08`
- 연월만 확인됨: `2000-08`
- 연도만 확인됨: `2000`
- 빈 값: 기존 값 유지
- 오타, 불가능한 날짜, 해석이 불명확한 값: 기존 값 유지 후 별도 검토

화면에서는 알려진 부분만 `2000년 08월 08일`처럼 표시합니다.
API는 새로 입력되는 잘못된 날짜를 거절하지만, 기존 잘못된 날짜를 그대로 둔 다른 항목 수정은 허용합니다.
엑셀의 실제 날짜 셀은 통합 문서의 1900/1904 날짜 체계로 읽습니다.
잘못된 날짜 숫자, 시간 전용 및 여러 구간이 섞인 사용자 지정 날짜 서식은 자동 해석하지 않고 확인이 필요한 값으로 표시합니다.
텍스트 `3/4/25`의 세기는 추정하지 않으므로 `2025-03-04`처럼 확인된 연도로 수정해야 합니다.

## 실행 순서

1. 새 코드를 배포하고 등록 및 수정 동작을 확인합니다. 구버전은 한글 날짜를 다시 저장할 수 있습니다.
2. 운영 DB의 최신 백업을 확보합니다. 백업 파일 읽기 검증은 실제 복원 시험과는 다릅니다.
3. Supabase SQL Editor에서 `normalize-publication-dates.sql` **전체**를 실행합니다.
   기본값 `'no'`는 미리보기이며 운영 테이블 값을 변경하지 않습니다.
4. 결과의 `old_value`, `new_value`를 확인합니다. `NEEDS_REVIEW_UNCHANGED` 항목은 자동 변경하지 않습니다.
5. 변환 결과가 맞으면 다음 한 줄만 바꾼 뒤 **전체 SQL**을 다시 실행합니다.

```sql
set local app.publication_dates_apply = 'yes';
```

6. 결과가 `NORMALIZED`인지 확인합니다. `CONCURRENT_EDIT_SKIPPED`는 실행 중 다른 수정이 있었던 행이므로 다시 미리보기로 검토합니다.
7. 도서 목록, 상세, 수동 등록, 엑셀 등록, 수정, ISBN 조회를 확인합니다.

이 SQL은 재실행해도 이미 표준화된 값은 바꾸지 않습니다. 임시 함수와 임시 테이블만 사용하고 영구 DB 구조는 변경하지 않습니다.
오류가 발생하면 중간 구문을 따로 실행하지 마세요. 같은 세션이 오류 상태라면 `ROLLBACK;` 후 원인을 확인합니다.

## 로컬 검증

```powershell
node scripts/check-publication-dates.mjs
node scripts/check-publication-date-migration.mjs "<temporary PGlite install>/dist/index.js"
```

SQL 테스트는 격리된 메모리 DB에서 미리보기, 변환, 오타 보존, 윤년, 부분 날짜, 재실행 및 기존 소장 정보 보존을 확인합니다.
운영 DB에는 테스트나 정리 SQL을 자동 실행하지 않습니다.
